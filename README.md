# F1 tyre degradation and pit-stop strategy

MMA3001 (Numerical Methods and Machine Learning) project: model Formula 1 tyre
degradation from race lap-timing data, validate the models on a withheld race,
and use the validated model to choose the pit-stop strategy that minimises
total race time.

## The engineering problem

A tyre gets slower as it wears, so lap time rises with tyre age. In raw lap
times this effect is mixed with others: the car gets lighter as fuel burns
(faster laps), safety cars and yellow flags slow laps down, and laps into and out
of the pits include the pit-lane time. The project:

1. removes the confounding effects (lap filtering, fuel correction, pit laps);
2. fits a degradation model per Pirelli compound (lap-time increase vs tyre age);
3. validates the models on laps they were not fitted to (leave-one-race-out
   cross-validation on 2022–2024, a single final test on 2025);
4. builds a race-time model and finds the pit lap(s) that minimise total race
   time, then tests how sensitive that answer is to the inputs.

Scope: Hungarian
Grand Prix, all teams, Pirelli compounds C3 and C4, seasons 2022–2025. Car
performance (downforce, top speed, set-up) is not modelled; a separate base
lap time per stint absorbs car and driver pace (D39).

All numerical methods (Euler, Heun, RK4, adaptive RK45, bisection, secant,
Newton–Raphson, finite differences, Gaussian elimination with partial
pivoting, linear least squares, KNN regression) are written from scratch with
NumPy in `src/tyredeg/numerics/` and `src/tyredeg/models/`. SciPy and
scikit-learn are used only in tests and benchmarks, to verify them.

Headline results (from the files above, current config):

- Selected model: a straight line in tyre age for both compounds. C3 wear rate
  0.0597 s/lap, C4 0.0551 s/lap (2023–2025 refit).
- Test on 2025: RMSE 0.94 s (C3) and 1.04 s (C4), lower than the no-degradation
  baseline, but with a positive bias (+0.28 and +0.54 s/lap). The bias criterion
  of 0.10 s/lap was not met.
  - **Main cause:** the 2025 wear rate was 30–36 % lower than in the training
    years.
  - **Second cause, C4 only:** the first laps of 2025 stints were slow, and they
    set each stint's base pace.
  - Extrapolation, the fuel correction and any single team are ruled out (D89).
- Audit: no data leakage, every strategy constraint holds, and an independent
  exhaustive search confirms the optimum (14 checks passed, D90).
- Strategy (70 laps): best two-stop (C3 → C4 → C4, pit laps 21 and 45)
  5926.50 s, best one-stop (pit lap 35) 5930.83 s, a gap of 4.33 s.
- The two-stop advantage disappears if the fuel coefficient is below
  0.0333 s/lap or the pit loss is above 25.22 s (`phase7_break_even.csv`).

## Installation

Requires Python 3.10 or newer (developed on 3.13, Windows 11).

```bash
py -3.13 -m venv .venv                       # or: python3 -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt   # Linux/macOS: .venv/bin/python
```

`requirements.txt` pins the direct dependencies (D11);
`requirements-lock.txt` freezes the whole environment.

## Running

All commands are run from the repository root.

```bash
# Whole workflow and every figure: numerics study -> load -> clean -> fuel-correct -> fit
# -> validate -> test -> optimise -> sensitivity -> audit -> benchmarks
.venv/Scripts/python scripts/run_pipeline.py

# A subset of stages (always run in pipeline order), e.g. everything except the benchmarks
.venv/Scripts/python scripts/run_pipeline.py --stages numerics data validate test strategy sensitivity audit
.venv/Scripts/python scripts/run_pipeline.py --config my_config.yaml --log-level DEBUG
```

- The first run downloads the race data into `cache/` (needs internet; OpenF1
  refuses free requests while a live F1 session is running). Later runs use
  the cache: about 1 min 45 s on the development laptop, of which the
  benchmarks take about 75 s (about 30 s without them).
- The log ends with the list of the figures written (24 per full run).
- The `audit` stage stops the run if a leakage or constraint check fails.
- The test race is evaluated **once**. After that, the `validate` stage only
  verifies that the cross-validation still selects the frozen models, and the
  `test` stage is skipped unless `--force-test` is given (every test run is
  logged in `reports/test_runs.log`; D55).
- Every run writes `reports/pipeline_manifest.json` and reports whether any
  result file changed since the previous run with the same config
  (reproducibility check, D83).
- The log is written to the console and to `reports/pipeline.log`
  (git-ignored, because it contains local paths).

Individual phases can also be run on their own: `scripts/numerics_study.py`
(Phase 3 method study), `scripts/compare_models.py --stage cv|test` (Phase 5),
`scripts/optimise_strategy.py` (Phase 6), `scripts/sensitivity_analysis.py`
(Phase 7), `scripts/benchmark.py` (Phase 8), `scripts/review_api.py`
(Phase 9 docstring review), `scripts/data_figures.py` and `scripts/audit.py`.

## Data and licensing

- Lap timing data are downloaded on demand through the
  [FastF1](https://docs.fastf1.dev/) library (2022, from its free data mirror)
  and the [OpenF1](https://openf1.org/) API (2023–2025). Since about
  15 October 2026, F1's own timing archive needs an F1 TV login and FastF1's
  free mirror only has 2021–2022, so only these free sources are used (D14,
  OI-1).
- The raw data and both caches (`cache/fastf1/`, `cache/openf1/`) are
  **not** in this repository (`.gitignore`). Formula 1 timing data belong to
  their rights holders; FastF1 and OpenF1 are unofficial community projects.
  Check their documentation for the current terms of use before using the data.
- `reference/pirelli_allocation.csv` was compiled for this project from the
  Pirelli and Formula1.com articles listed in its `source_url` column.
- The result tables in `reports/` contain only derived statistics.

## Alternative solutions

For each step of the problem, two or more methods were built and compared on
the same data. Every number below comes from the result file named in the
last column, and is regenerated by the pipeline. Section 5 of the report
discusses the same comparison.

| Step | Alternatives compared | Result | Chosen | Source |
|---|---|---|---|---|
| Degradation model | Baseline (no degradation), polynomial degree 1/2/3, wear ODE, KNN (k = 10–400, uniform or distance weights) | Leave-one-race-out RMSE, C3: baseline 1.17 s, polynomial degree 1 0.633 s, wear ODE 0.633 s, best KNN 0.639 s. C4: baseline 1.13 s, degree 1 0.851 s, degree 2 0.849 s, wear ODE 0.849 s. Degree 2 and the wear ODE fail the C4 bias check; most KNN models fail the monotonic check | Polynomial degree 1 for both compounds: one-standard-error rule (the simplest family winner whose RMSE is within one SE of the best) | `phase5_cv_summary.csv`, `model_selection.json` |
| ODE solver (wear model) | Euler, Heun, RK4, adaptive RK45, closed form | To reach an error of about 1e-8: RK4 needs 256 f-evaluations (h = 0.625), RK45 103 (rtol = 1e-8), Euler and Heun did not reach it at any step tested (Euler 9.7e-4 and Heun 9.5e-8 with 4096 steps). The closed form takes 0.009 ms | RK4 with h = 1 lap in the wear model (`config.yaml`, `solver: rk4`); RK45 and the closed form are options and cross-checks | `phase8_ode.csv` |
| Least squares | Normal equations (mine), QR (NumPy QR + my back substitution), SVD (`numpy.linalg.lstsq`) | Degree 6, unscaled ages: relative errors 3.6e-9 / 5.1e-13 / 1.7e-10. With ages scaled to [-1, 1], all three ≤ 2.3e-13 | My normal equations on scaled ages | `phase8_least_squares.csv` |
| Root finder for the ODE parameter b | Bisection, secant, Newton | Same b for each compound (to within 1e-8); 21 / 5 / 3 iterations | Bisection (the default): always converges inside the bracket from the grid search; secant and Newton are faster but are kept as cross-checks | re-run of `WearODEModel(root_finder=...)` on the training races |
| One-stop pit lap | Brute force, secant, Newton | With the stint-length limits: 6 / 9 / 18 function evaluations, same pit lap (35). Without the limits: 69 / 12 / 21 evaluations, secant 5.9× faster than brute force | Brute force (only 6 feasible laps; exact and simplest) | `phase6_methods.csv`, `phase8_strategy.csv` |
| KNN search | My brute-force KNN, scikit-learn kd-tree | Identical predictions (difference ≤ 1.8e-15). Time grows as n^1.07 against n^0.23; peak memory at n = 16,000 is 270 MB against 1.4 MB | My brute force (data sets are small; method required from scratch) | `phase8_knn.csv` |
| Data source | FastF1 free mirror + OpenF1, or F1 TV timing archive | The free sources cover 2022–2025 with no login | Free sources only | see *Data and licensing* |

## Limitations

- **One circuit, two compounds.** The model is fitted to the Hungaroring only.
  Degradation depends on track surface, layout and temperature, so the
  parameters do not transfer to other circuits.
- **Year-to-year change is the largest error.** The 2025 test race degraded
  30–36 % less than the training races. The models were biased on the test
  (+0.28 / +0.54 s/lap), and on 2025 the selected line has a negative test R²
  (−0.04 for C3, −0.47 for C4), so it explains less variance than a constant
  per stint. The strategy result can change with the year (Phase 7).
- **Anchoring on the first laps.** Each held-out stint's base pace comes from
  its first 3 laps (D49). In 2025 the C4 first laps were about 0.2 s slow
  (warm-up or traffic), which adds about +0.24 s/lap to the C4 bias (D89).
- **Fuel coefficient.** `k_fuel` is a single value for all races (0.046 s/lap,
  estimated from the training data and close to a rule of thumb, D22), and it
  also absorbs track evolution (D22 restatement). The fitted wear rate depends on it
  one-for-one (d rate / d k_fuel = 1), and the two-stop decision flips below
  0.0333 s/lap.
- **Not modelled:** track temperature, weather, car performance and set-up,
  driver style, traffic and dirty air, tyre warm-up, safety-car timing, tyre
  set availability, and used tyres at the start of a stint. Base pace per stint
  absorbs car and driver differences only as a constant.
- **Stint-length limits** come from the data (C3 ≤ 40, C4 ≤ 35 laps with at
  least 5 laps observed at that age), and they bind for the one-stop strategy.
- **Few races.** Three training races give only three cross-validation folds,
  and one test race gives a noisy test metric.
- **Input checks are guards, not proofs.** Every public function has a
  complete NumPy docstring and checks its inputs (`scripts/review_api.py`,
  `reports/phase9_api_review.csv`), but the checks cover types, shapes and
  ranges, not whether the data make physical sense.

The challenges met during the project, how they were resolved and the lessons
drawn from them are discussed in the project report (submitted separately).

## Use of AI

**Tool.** Claude Code (Anthropic), the VS Code extension with the model Claude
Opus 5.5, used for the whole project.

**What it was used for, and how much.**
- **Code: almost all of it.** The AI wrote essentially all of the code in this
  repository: the from-scratch numerical methods, the data loaders, the models,
  validation, strategy, sensitivity and performance code, the scripts and the
  940 tests.
- **Analyses:** the AI ran every analysis that produced the numbers in `reports/`.
- **Writing:** the AI drafted the working documentation (a decision log, a
  challenge log and a lessons summary), this README and the report.
- **My part:** the project specification and the working rules it had to follow,
  every Phase 1–5 decision, the questions that changed the
  analysis, and the review of each phase before committing it.

**Why AI was used this way.** The project requires every numerical method to be
written from scratch, tested and documented. That is a large amount of code, so
I used the AI to implement it. I kept control of the engineering through a
decision protocol. For each phase the AI had to list every decision with 2–3
options, a recommendation, the evidence and how it would be validated, and then
**stop until I approved or changed it** (Phases 1–5). For Phases 6–9 I let the AI
decide and implement directly, under the rule that every such decision is marked
"Decided by AI without prior approval, to be reviewed by me" in the decision log.

**Decisions that remained mine:**
- **Scope:**
  - I asked for data surveys of every track and every Pirelli compound before
    choosing.
  - I then chose the Hungaroring and compound C3, later adding C4.
  - I chose all teams instead of Red Bull only, deliberately not modelling car
    performance.
  - I chose to use free data sources only.
- **Methods:**
  - I asked for a step-size study to find the optimal finite-difference step
    (N3).
  - I asked for alternative methods to be tried and compared (N7, N12).
  - I chose the near-singular threshold of 1e12.
  - I chose the cleaning, fuel and pit-loss options of Phase 2.
  - I first chose a strict root-finder stopping rule. The AI then showed that it
    can fail to stop, so I approved the round-off safeguard.
- **Questions that changed the analysis:**
  - Whether track temperature should be a model input, and which other
    tyre-wear factors were missing. These led to the documented factor reviews.
  - How to handle the failed bias criterion on the 2025 test race.
- **Publication:** making the repository public and rewriting the git history
  to remove local paths.

**How the AI's work was checked.**
- **Numerical methods:** every from-scratch method is tested against SciPy,
  scikit-learn, `numpy.linalg.lstsq` or an analytic solution. The observed
  orders of convergence match the theory: Euler 1.0, Heun 2.0, RK4 4.0.
- **Models:** the models were chosen by leave-one-race-out cross-validation.
  The test race was evaluated only once, behind a firewall that the code
  enforces.
- **Audit:** an audit stage checks for data leakage and checks the pit-stop
  constraints with an independent exhaustive search.
- **Reproducibility:** a fresh clone from GitHub reproduced all 52 result files
  byte for byte.
- **My own checks:** I read each phase summary, which listed every assumption
  and uncertainty, before I approved the commit. I asked for explanations of
  anything I could not yet defend, such as the interquartile range (IQR) and the
  purpose of a validation test.

**Errors and limitations of the AI** (each was caught and fixed during the project):
- It wrote doctest examples and expected values without running them, and some
  failed (C3, C11).
- A verification re-run it started overwrote the frozen model selection after
  the test. It was restored from git and a guard was added (C16).
- It leaked my local file paths into generated files three times (C17, C19,
  C20).
- It left 126 public objects with incomplete docstrings, against the project's
  own rule, until a review script found them (C22).
- It left a docstring that contradicted a later decision (C23).
- It did not anticipate that the F1 data archive would be locked, or that the
  first chosen compound had no data, so the scope changed three times in
  Phase 1.
- Its first root-finder stopping rule could fail to stop (D30 amendment).

**Effect on my understanding and workflow.**
- The protocol turned the AI from a code generator into something that
  explained options I had to choose between. I learned the methods through
  those choices: why central differences beat forward differences, why the
  normal equations lose accuracy as the condition number grows, and why
  cross-validation within past seasons cannot detect a change between seasons.
- The AI's mistakes showed me that output that looks plausible is not verified
  output. A test written from an expected value nobody computed proves nothing.
- Every generated file has to be checked before it is published.
- Because I must explain this work without AI in the oral examination, I
  treated every decision as something I need to be able to defend myself.
